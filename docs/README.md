# 文書の案内

初めて使う場合は導入・運用手順を、利用動作を確認するときは要件を、コードの責務を確認するときはアーキテクチャを開く。

## 読む文書

| 文書                                     | 種別 | 読み手と用途                                         | 決定状態                     |
| ---------------------------------------- | ---- | ---------------------------------------------------- | ---------------------------- |
| [プロジェクトの入口](../README.ja.md)    | 説明 | 利用できる環境と導入の入口を知る                     | 現在の構成                   |
| [Windows・Linux での導入と運用](installation.md) | 手順 | 利用者が導入、接続、更新、切り戻しを行う | 手動導入 |
| [CONTRIBUTING](../CONTRIBUTING.md)       | 手順 | 保守者が開発環境を用意し、検証と導入版の準備を行う   | 現在の開発手順               |
| [ストアへの掲載](store-listing.md)       | 手順 | 所有者が Obsidian と Chrome Web Store に申請する     | 未申請                       |
| [要件](requirements.md)                  | 参照 | 利用者と実装者が、動作、範囲、受入条件を確認する     | 承認した振る舞い             |
| [アーキテクチャ](architecture.md)        | 説明 | 実装者が、責務、記録の正本、接続と検証経路を確認する | 実装と確認済み・未確認の範囲 |

## 根拠と実装を区別する

実装は `core/`、`contracts/`、`libs/`、`runtimes/`、検査は `core/` と `runtimes/` のテストおよび `tests/` にある。

## 検証の読み方

[要件の追跡](requirements.md#要件の追跡)は要件の索引である。実際の受入結果と機械検査の分担は[アーキテクチャ](architecture.md#検証)に記す。

## 文書の保持

`docs/`には継続する読み手に必要な手順、要件、説明を置き、調査、試行、作業計画は追跡しない`work/`へ分ける。
要件は受入条件が実装と検査へ移され、この参照文書を読む必要がなくなった時点で取り除く。
構成や機構の説明は、対応するコードと契約だけで読み手の判断が完結するようになった時点で取り除く。
文書を取り除くときは、必要な意味と参照先を先に更新する。
